# Shelf Tools: how it works

One HTML page, `index.html`, with its scripts and data inside it. GitHub Pages serves it as it is; opened from disk it works the same. There is no server and no network use apart from the fonts. Recap and the Workshop only read files; [Sync](#sync) reads and writes two folders the browser was given.

## Reading the Memory Stick

A picked folder gives the browser a list of every file in it with its path. The page keeps only the paths under the five plugin folders and finds the stick's root as the folder above them, so the drive itself, a folder holding a copy, or the five folders dropped on their own all work. On a PS Vita the same folders sit inside `pspemu`, which is picked in place of a drive; nothing in the reading differs.

Dropped folders are walked with the browser's entries API. A drop's entries can only be taken while the drop is being handled, so they are all taken first and the folders read afterwards.

A zip is read through its central directory. An entry is inflated with the browser's own `DecompressionStream`, and only as far as needed: 404 bytes of a 20 MB save state.

| Plugin | Read from | Used for |
|---|---|---|
| Shelf | `SHELF/CACHE/LIBRARY.BIN` | Every game's path, title, disc ID and type; the folder it sits in |
| Shelf | `SHELF/CACHE/<key>.IMG` | Icons: the first 144 × 80 RGB565 picture after an 8-byte header |
| Shelf | `SHELF/games.txt` | `path \| last started \| finished \| hidden \| picture \| favourite`, times in minutes since 2000 |
| Sidequest | `SIDEQUEST/<folder>/SUSPEND.SQS`, `STATE1..5.SQS` | The slot header only: title at 100, disc ID at 228, saved at 244, game path at 276. Size from the file |
| Sidequest | `.THM` beside each slot | `SQT1`, width, height, RGB565 |
| Checkpoint | `CHECKPOINT/JOURNEY/<id>.TXT` | `date \| time played \| description \| save` |
| Checkpoint | `CHECKPOINT/JOURNEY/<id>.TIM` | Seconds played |
| Checkpoint | `CHECKPOINT/<save>/<YYYYMMDD_HHMMSS>/` | One kept version each; `<stamp>.PIN` beside it when pinned. The game is the first nine characters of the save folder |
| Emblem | `EMBLEM/games/<id>.txt` | Run through the engine: which achievements count, their points |
| Emblem | `EMBLEM/earned/<id>.txt` | `n \| date \| title \| N pts`. A number listed twice keeps its first date; numbers the game file does not count are left out, as the viewer does |
| Runtime | `RUNTIME/battery.log` | One line per power-on: start, end, time awake, time asleep, battery |
| Runtime | `RUNTIME/uptime.txt` | The power-on in progress, which is not in `battery.log` until it ends: start, last look, battery and minutes asleep |
| Runtime | `RUNTIME/battery_use.log` | Battery at every program start (`start <ISO file name>` or the EBOOT's folder), on waking and every 5% |
| Shelf | `SHELF/battery.log` | Used only when Runtime's is missing: Shelf's own power-on lines |

Every file is read inside a guard: one that cannot be read is skipped, noted, and named in the Load window, and the rest still loads.

A game is known by its disc ID. Shelf's library ties the ID to a path, which is how Sidequest's slots (by path) and Runtime's starts (by file name) find their game. Runtime has room for 47 characters of a name, so a longer file name arrives cut short. A whole name must match exactly; a name that fills that room is matched to the game whose name begins with it, and when several do, to the one with a dated save, journey entry, unlock or slot nearest the session.

A program Runtime saw that Shelf's library does not hold (an older ISO, a PS1 game) becomes a game of its own, named from its file.

### Dates without a year

Runtime writes `Tue Nov 24 03:30`. The lines are in order, so the page reads them from the last one back, starting from the date the file was last changed: each line gets the latest year, no later than the line after it, whose calendar puts that weekday on that date. A weekday and a date repeat only every few years, so this is exact unless the PSP's clock was wrong.

## Time played

For each game, two counts:

- **Checkpoint.** Each journey line holds the game's running total of play. The total at the end of a period, less the total at its start, is the period's share. The `.TIM` file is newer than the last line; the difference goes to the period of the game's last activity. For all time, the `.TIM` total itself.
- **Runtime.** A `start` line opens a session for that program. It ends at the next `start` or `power on`, or at the end of its power-on, and never runs longer than the time awake left in that power-on.

Recap uses the larger of the two. They measure the same play from two sides, so adding them would count it twice.

The calendar of days uses Runtime's sessions for a game Runtime has seen, and the journey for one it has not (the play between two lines goes on the day of the second). Hours of the day and weekdays are minutes of Runtime's sessions; with no Runtime at all, they count when journey lines, unlocks and save versions happened instead.

## The share picture

Drawn on a canvas, 1080 × 1350, from the same numbers, and turned into a PNG in the browser.

## Emblem's engine in the page

`em.c` has no PSP calls and no C library calls; the plugin builds the same file for its PC tests. `engine/build.sh` compiles it with clang for WebAssembly, together with `emglue.c`, and binaryen's `wasm2js` turns that into plain JavaScript (`src/emblem-engine.js`). Plain JavaScript runs in every browser and under any page policy, where WebAssembly may be refused.

`emglue.c` does what the plugin's `main.c` does around the engine: memory reads (with the plugin's own checks: outside the game's RAM or unaligned gives 0), and error lines collected with their line numbers. The page decides what memory holds: all zeros, all `0xFF`, or a dump.

`tests/native_driver.c` builds the same `em.c` and `emglue.c` with gcc, and `tests/test_engine.js` prints the same lines from the page's engine, for every released game file and a file of deliberate mistakes: errors, achievements, pool use, and three seconds over zeros and over `0xFF`. `run_tests.sh` checks that the two outputs are identical byte for byte.

### The Workshop's views

The text is the only copy. The Achievements and Names tabs read its lines (`game`, `N | title | points | rule`, `when`, `show`, `name = ...`) and an edit in a row rewrites that one line. Every change is checked 0.2 s later.

## Sync

Sync brings one Memory Stick and the **vault** level. The vault is a folder on the computer, laid out like a Memory Stick, that holds the newest of everything. Devices are never compared with each other: each is synced with the vault, and the vault passes on what the others added.

It runs in three steps, and only the third writes.

1. **Scan.** Each side is read: every file of every save folder is hashed (SHA-256), and the plugin files are read as text.
2. **Plan.** For each thing, what each side is missing, by the rules below. Nothing is written. The plan is what the page shows, and each line can be switched off.
3. **Apply.** The lines that are on are carried out.

### What is on each side

| Where | Holds |
|---|---|
| Memory Stick `SYNC/STATE.JSON` | The device's ID and name, the vault it was last synced with, and what the two agreed on then: each save's and Emblem game file's fingerprint, and Shelf's marks. While saves are being written to the device, the list of them (`pending`) |
| Vault `SYNC/VAULT.JSON` | The vault's ID, the devices it knows, where each save came from and its date, Shelf's marks by disc ID, and for every game the total time played with where each device stood when it was last synced |
| Vault `PSP/SAVEDATA`, `EMBLEM`, `CHECKPOINT/JOURNEY` | The newest copy, in the same layout as a Memory Stick |
| Vault `SYNC/history/<save>/<date>_<code>/` | The last 5 copies of a save that Sync replaced on either side |
| Vault `SYNC/devices/<device ID>/` | Each device's Runtime logs |
| Vault `SYNC/log.txt` | One line per sync |

Folder and file names are matched without regard to upper and lower case, as the Memory Stick does. Files are written into the folders that are already there.

### The rules

**Saves** (`PSP/SAVEDATA/<name>` where the name starts with a disc ID, up to 32 MB) and **Emblem game files** are whole things with a fingerprint: the hash of a folder's file names, sizes and hashes. With `s` the Memory Stick's, `v` the vault's and `b` what they agreed on last time:

| | Result |
|---|---|
| `s` = `v` | Nothing |
| Only on one side, never synced | Copied to the other |
| Only in the vault, and `b` says it was on the device | Removed here: left alone unless ticked |
| `b` = `v`, `s` differs | The device changed it: to the vault |
| `b` = `s`, `v` differs | Another device changed it: to this device |
| Neither | Both changed, or a first sync: you choose. The newer date is offered |

**Achievements** (`EMBLEM/earned/<id>.txt`) are joined by number. One on both sides keeps the earlier date, the same rule Emblem has for a number listed twice in one file.

**Time played** is a count that each device adds to, so the same play must never be added twice. The vault notes, for each game and each device, where the device's count stood when it was last synced and where the vault's stood. The device's play since then is its count now less that; the new total is the vault's total plus it. On a first sync there is no such note: lines both journeys hold, with the same total, are shared history and counted once, and the rest is added.

**Journey lines** are joined, keyed by date, text and save. A line's total is the game's total at that moment on the device that wrote it, so lines new to each side are put in date order and their totals recalculated from how much play each added on its own side. A line both sides already hold is not changed.

**Shelf's marks** (`SHELF/games.txt`) are matched by disc ID through Shelf's library on the device. Last started is the later of the two. Favourite, completed and hidden take the device's value if it changed since the last sync, and the vault's if not. The picture setting is not synced.

A device is given plugin files only if it has that plugin's folder, or Shelf to show them.

### The order of writing

1. The device's `STATE.JSON`, with the saves on it that are about to be replaced. A Memory Stick that cannot be written stops the sync here, with nothing changed.
2. The vault's `VAULT.JSON`, with every game's new total and "this device was at X, is being given Y". From here on, the same play cannot be added twice, whatever is cut short.
3. Everything bound for the vault, then everything bound for the device. A save folder is read whole and checked against the scan before anything is written, the copy it replaces goes to the history first, files no longer in the save are removed, and what was written is read back and compared.
4. Both state files again, as things now stand.

If a sync stops after step 2, the next scan finds the note from step 2: a device count that reached Y was written, one that did not was not, and its play is counted from the right place either way. A save in `pending` that differs from the vault's is offered as "take the vault's", since what is on the device may be half of each.

### The sample

**Try it on the sample** builds a PSP and a vault in memory by running Sync itself: the sample Memory Stick is synced, a PS Vita is, both are played on, and the Vita is synced again. The page then compares the PSP. Nothing is written anywhere.

## The sample Memory Stick

`tools/make_sample_stick.py` writes a year of made-up play for eight real game titles into `tests/sample/ms0`, in the exact formats above, with pictures drawn by the script and the real Emblem game files. Save states are their 4 KB header only; `tests/sample/sizes.txt` gives the sizes real ones would have. `tools/build.py` packs it into the page as gzip'd JSON (icons cut to the part the page reads).

## Tests

`tests/run_tests.sh`:

1. With `../psp-ark-plugins` beside this repository: `engine/em.c`, `em.h` and `games/` are identical to the plugins repo's.
2. The page's engine answers like `em.c` built with gcc, on every game file.
3. `tests/test_stick.js`: the sample Memory Stick read as a folder, as a zip (made in the test, inside a folder, deflated) and as dropped folders, every reader checked against the files themselves, the year-less dates (including a year boundary), the power-on in progress, a damaged file being skipped, and Recap's numbers (the months add up to all time).
4. `tests/test_sync.js`: Sync on real folders. A PSP (the sample Memory Stick with saves), a PS Vita (lower-case folders, another file name for the same game) and a vault go through first syncs, play on each device, a save changed on both, a removed save, a save changed between Compare and Sync, a write that fails half-way through a save, play time cut short before and after the device's file was written, a Memory Stick that cannot be written, a second vault, and the history's limit. ARK's folder and installed game data stay out.
5. The page is built.

`tests/browser_check.py` (optional) loads the zip through the file picker in headless Chrome, edits a rule until it breaks and back, adds an achievement, uses a code note, downloads the file and makes the share picture. It then runs Sync: the sample, and a real run through the browser's own folder writing, with the two folder pickers answered by folders in the browser's private storage.
