# Shelf Tools: how it works

One HTML page, `index.html`, with its scripts and data inside it. GitHub Pages serves it as it is; opened from disk it works the same. There is no server and no network use apart from the fonts.

## Source layout

| File | Does |
|---|---|
| `src/page.html` | The page: markup and styles. `tools/build.py` puts the scripts in at `<!--SCRIPTS-->` |
| `src/stick.js` | The Memory Stick as files with paths, sizes and partial reads: from a picked folder, dropped folders, a zip, or the packed sample |
| `src/parse.js` | Reads every plugin's files into one model (below) |
| `src/stats.js` | Recap's numbers for one period |
| `src/ui.js` | Tabs, the loader, icons and pictures, shared helpers |
| `src/recap.js` | Recap's sections and the share picture |
| `src/workshop.js` | The Emblem Workshop |
| `src/engine.js` | A small wrapper around the engine: check a file, run it over memory |
| `src/emblem-engine.js` | Generated by `engine/build.sh`: Emblem's `em.c` as JavaScript |
| `engine/` | `em.c` and `em.h` (Emblem's, unchanged), `emglue.c` (what the plugin's `main.c` gives the engine: memory reads, error lines) |
| `games/` | Emblem's released game files, offered under Open |
| `tools/` | `build.py`, `make_sample_stick.py`, `sync_from_plugins.sh` |
| `tests/` | PC tests (`run_tests.sh`), the browser check, the sample Memory Stick |

## Reading the Memory Stick

A picked folder gives the browser a list of every file in it with its path. The page keeps only the paths under the five plugin folders and finds the stick's root as the folder above them, so the drive itself, a folder holding a copy, or the five folders dropped on their own all work.

Dropped folders are walked with the browser's entries API. A drop's entries can only be taken while the drop is being handled, so they are all taken first and the folders read afterwards.

A zip is read through its central directory. An entry is inflated with the browser's own `DecompressionStream`, and only as far as needed: 404 bytes of a 20 MB save state.

| Plugin | Read from | Used for |
|---|---|---|
| Shelf | `SHELF/CACHE/LIBRARY.BIN` | Every game's path, title, disc ID and type; the folder it sits in |
| Shelf | `SHELF/CACHE/<key>.IMG` | Icons: the first 144 × 80 RGB565 picture after an 8-byte header |
| Shelf | `SHELF/games.txt` | `path \| last started \| finished \| hidden \| picture \| favourite`, times in minutes since 2000 |
| Sidequest | `SIDEQUEST/<folder>/SUSPEND.SQS`, `STATE1..5.SQS` | The slot header only: title at 100, disc ID at 228, saved at 244, game path at 276. Size from the file |
| Sidequest | `.THM` beside each slot | `SQT1`, width, height, RGB565 |
| Checkpoint | `CHECKPOINT/JOURNEY/<id>.TXT` | `date \| time played \| description \| save` |
| Checkpoint | `CHECKPOINT/JOURNEY/<id>.TIM` | Seconds played |
| Checkpoint | `CHECKPOINT/<save>/<YYYYMMDD_HHMMSS>/` | One kept version each; `<stamp>.PIN` beside it when pinned. The game is the first nine characters of the save folder |
| Emblem | `EMBLEM/games/<id>.txt` | Run through the engine: which achievements count, their points |
| Emblem | `EMBLEM/earned/<id>.txt` | `n \| date \| title \| N pts`. A number listed twice keeps its first date; numbers the game file does not count are left out, as the viewer does |
| Runtime | `RUNTIME/battery.log` | One line per power-on: start, end, time awake, time asleep, battery |
| Runtime | `RUNTIME/uptime.txt` | The power-on in progress, which is not in `battery.log` until it ends: start, last look, battery and minutes asleep |
| Runtime | `RUNTIME/battery_use.log` | Battery at every program start (`start <ISO file name>` or the EBOOT's folder), on waking and every 5% |
| Shelf | `SHELF/battery.log` | Used only when Runtime's is missing: Shelf's own power-on lines |

Every file is read inside a guard: one that cannot be read is skipped, noted, and named in the Load window, and the rest still loads.

A game is known by its disc ID. Shelf's library ties the ID to a path, which is how Sidequest's slots (by path) and Runtime's starts (by file name) find their game. Runtime has room for 47 characters of a name, so a longer file name arrives cut short. A whole name must match exactly; a name that fills that room is matched to the game whose name begins with it, and when several do, to the one with a dated save, journey entry, unlock or slot nearest the session.

A program Runtime saw that Shelf's library does not hold (an older ISO, a PS1 game) becomes a game of its own, named from its file.

### Dates without a year

Runtime writes `Tue Nov 24 03:30`. The lines are in order, so the page reads them from the last one back, starting from the date the file was last changed: each line gets the latest year, no later than the line after it, whose calendar puts that weekday on that date. A weekday and a date repeat only every few years, so this is exact unless the PSP's clock was wrong.

## Time played

For each game, two counts:

- **Checkpoint.** Each journey line holds the game's running total of play. The total at the end of a period, less the total at its start, is the period's share. The `.TIM` file is newer than the last line; the difference goes to the period of the game's last activity. For all time, the `.TIM` total itself.
- **Runtime.** A `start` line opens a session for that program. It ends at the next `start` or `power on`, or at the end of its power-on, and never runs longer than the time awake left in that power-on.

Recap uses the larger of the two. They measure the same play from two sides, so adding them would count it twice.

The calendar of days uses Runtime's sessions for a game Runtime has seen, and the journey for one it has not (the play between two lines goes on the day of the second). Hours of the day and weekdays are minutes of Runtime's sessions; with no Runtime at all, they count when journey lines, unlocks and save versions happened instead.

## The share picture

Drawn on a canvas, 1080 × 1350, from the same numbers, and turned into a PNG in the browser.

## Emblem's engine in the page

`em.c` has no PSP calls and no C library calls; the plugin builds the same file for its PC tests. `engine/build.sh` compiles it with clang for WebAssembly, together with `emglue.c`, and binaryen's `wasm2js` turns that into plain JavaScript (`src/emblem-engine.js`). Plain JavaScript runs in every browser and under any page policy, where WebAssembly may be refused.

`emglue.c` does what the plugin's `main.c` does around the engine: memory reads (with the plugin's own checks: outside the game's RAM or unaligned gives 0), and error lines collected with their line numbers. The page decides what memory holds: all zeros, all `0xFF`, or a dump.

`tests/native_driver.c` builds the same `em.c` and `emglue.c` with gcc, and `tests/test_engine.js` prints the same lines from the page's engine, for every released game file and a file of deliberate mistakes: errors, achievements, pool use, and three seconds over zeros and over `0xFF`. `run_tests.sh` checks that the two outputs are identical byte for byte.

### The Workshop's views

The text is the only copy. The Achievements and Names tabs read its lines (`game`, `N | title | points | rule`, `when`, `show`, `name = ...`) and an edit in a row rewrites that one line. Every change is checked 0.2 s later.

## The sample Memory Stick

`tools/make_sample_stick.py` writes a year of made-up play for eight real game titles into `tests/sample/ms0`, in the exact formats above, with pictures drawn by the script and the real Emblem game files. Save states are their 4 KB header only; `tests/sample/sizes.txt` gives the sizes real ones would have. `tools/build.py` packs it into the page as gzip'd JSON (icons cut to the part the page reads).

## Tests

`tests/run_tests.sh`:

1. With `../psp-ark-plugins` beside this repository: `engine/em.c`, `em.h` and `games/` are identical to the plugins repo's.
2. The page's engine answers like `em.c` built with gcc, on every game file.
3. `tests/test_stick.js`: the sample Memory Stick read as a folder, as a zip (made in the test, inside a folder, deflated) and as dropped folders, every reader checked against the files themselves, the year-less dates (including a year boundary), the power-on in progress, a damaged file being skipped, and Recap's numbers (the months add up to all time).
4. The page is built.

`tests/browser_check.py` (optional) loads the zip through the file picker in headless Chrome, edits a rule until it breaks and back, adds an achievement, uses a code note, downloads the file and makes the share picture.
